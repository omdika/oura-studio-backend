# Version 3.57 - Perbaikan Performa API Tambah Stok & Edit Produk (stock-from-bahan & PATCH sizes)

## 1. Problem / Opportunity
*   **Context:** Dua endpoint yang sering dipakai operator di tab Produk — `POST /products/{sku}/sizes/{size_id}/stock-from-bahan` (Tambah Stok dari Bahan) dan `PATCH /products/{sku}/sizes/{size_id}` (edit stok/harga/manual HPP) — dilaporkan *memakan waktu terlalu lama* (user merasakan >2-3 detik, kadang timeout di iOS). Investigasi kode (`app/routers/products.py:907-1053`, `app/routers/products.py:835-860`, `app/routers/production.py:229-273`) menunjukkan keduanya melakukan **banyak round-trip DB serial** di atas koneksi Supabase cross-region (Cloud Run `asia-southeast2` Jakarta ↔ DB `ap-northeast2` Seoul, ~100-150 ms/round-trip) **plus agregasi `stock_ledger` tanpa indeks**.
*   **Hipotesis terverifikasi dari inspeksi kode (belum EXPLAIN ANALYZE live, perlu konfirmasi di Phase implementasi):**
    1.  **Missing index `stock_ledger.product_size_id` (+ `created_at`).** Tabel `stock_ledger` tidak punya indeks selain PK `id` (cek `alembic/versions/900130a6de91_initial_schema.py:146-157` dan `grep create_index`: hanya 5 indeks di seluruh repo, tidak ada untuk `stock_ledger`). Setiap `SUM(change_qty) WHERE product_size_id = ?` (`_current_stock_qty:98-103`, `_stock_breakdown_map:106-124`, `_stock_qty_map:85-94`) melakukan **Seq Scan** di Postgres. Saat ledger tumbuh (ribuan baris), ini jadi bottleneck linear.
    2.  **Missing index `production_batch_item.product_size_id` & `production_batch.status`.** `_latest_production_item:131-148` dan `_latest_hpp_map:151-164` JOIN `production_batch_item` + `production_batch` filter `product_size_id IN (...)` + `status='confirmed'` + `ORDER BY confirmed_at DESC`. Tanpa indeks, planner scan seluruh tabel.
    3.  **Missing index `material_purchase.material_id` + `purchased_at`.** FIFO deduction (`products.py:1020-1037` dan `_fifo_deduct_hardware:251-257`) selalu `SELECT ... WHERE material_id = ? ORDER BY purchased_at, created_at`. Tanpa indeks, scan + sort.
    4.  **Waterfall N+1 round-trip.** `stock-from-bahan` menjalankan ~10-13 query serial: `get_product` (1) + `get_size` (1) + `get_spec` (1) + `find purchase(s)` (1) + `per-component FIFO SELECT all purchases` (k × 1) + `INSERT ledger + COMMIT` (1) + `_size_detail_out` (5 query lagi: `_current_stock_qty`, `_stock_breakdown`, `_latest_production_item`, `_fabric_items_map`, `_hardware_items_map`). Total ~1.3-1.8 s latency jaringan murni sebelum compute. `PATCH` serupa: `get_product` + `get_size` + `COMMIT` + `_stock_breakdown` + `_current_stock_qty` = 5 round-trip, 2 di antaranya agregasi tanpa indeks.
    5.  **Redundant double aggregation di PATCH.** `PATCH` memanggil `_stock_breakdown` (CASE SUM) dan `_current_stock_qty` (SUM) terpisah — bisa dijadikan satu query (`SUM(change_qty)` + `SUM(CASE ...)`) untuk hemat 1 round-trip.
*   **Objective:** Turunkan p95 latency kedua endpoint dari detik-an ke <400 ms di jaringan cross-region yang sama, tanpa mengubah kontrak response (tetap return `ProductSizeDetailOut` / `ProductSizeOut`), dengan fondasi indeks yang mencegah regresi saat ledger & purchase bertambah.

## 2. User Flow & UX Specifications
*   **Entry Point:**
    *   **Tambah Stok:** `ProdukSizeDetailView` → Sheet "Tambah Stok dari Bahan" → pilih `qty` (+ optional `spec_id`/`material_purchase_id`) → `POST /products/{sku}/sizes/{size_id}/stock-from-bahan`.
    *   **Edit Produk:** `ProdukSizeDetailView` → Edit Harga / Manual HPP / Reorder Min Qty → `PATCH /products/{sku}/sizes/{size_id}`.
*   **UI Components:** Tidak ada perubahan UI. Namun loading state di iOS (`canSave` + `.disabled` + spinner) harus tetap responsif — backend harus kembalikan <400 ms agar tidak trigger timeout `URLSession` (60 s) atau perceived hang.
*   **Validation Rules (`canSave`):** Tidak berubah. `qty > 0`, `selling_price >= 0`, `manual_hpp_*` nullable numeric.
*   **State & Progressive Disclosure:** Tidak berubah. Spec ini pure backend perf — tidak menambah field/param baru di request.

## 3. Database Schema Changes (FastAPI / SQLAlchemy)
*   **Affected Tables:** `stock_ledger`, `production_batch_item`, `material_purchase`, `production_batch`, `product_size`.
*   **Migrasi baru `alembic/versions/<rev>_perf_indexes_stock_and_hpp.py`:**
    ```python
    # stock_ledger — hot path untuk semua stock qty lookup
    op.create_index('ix_stock_ledger_product_size_id', 'stock_ledger', ['product_size_id'])
    op.create_index('ix_stock_ledger_product_size_reason', 'stock_ledger', ['product_size_id', 'reason'])
    op.create_index('ix_stock_ledger_created_at', 'stock_ledger', ['created_at'])
    # production_batch_item — latest HPP lookup
    op.create_index('ix_pbi_product_size_id', 'production_batch_item', ['product_size_id'])
    op.create_index('ix_pbi_batch_id', 'production_batch_item', ['production_batch_id'])
    # production_batch — status filter
    op.create_index('ix_production_batch_status', 'production_batch', ['status'])
    op.create_index('ix_production_batch_confirmed_at', 'production_batch', ['confirmed_at'])
    # material_purchase — FIFO deduction
    op.create_index('ix_material_purchase_material_id', 'material_purchase', ['material_id'])
    op.create_index('ix_material_purchase_material_purchased', 'material_purchase', ['material_id', 'purchased_at'])
    # product_size — lookup per product
    op.create_index('ix_product_size_product_id', 'product_size', ['product_id'])
    ```
    *Catatan:* Nama indeks `ix_*` konsisten dengan konvensi Alembic di repo (`ix_material_fabric_family`). Tidak menambah constraint, hanya B-Tree index — downtime 0, `CONCURRENTLY` tidak perlu di Supabase managed (tapi pertimbangkan `op.create_index(..., postgresql_concurrently=True)` jika tabel >1M rows).
*   **Model changes (`app/models/*.py`):** Tambah `__table_args__` atau `Index(...)` di `StockLedger`, `ProductionBatchItem`, `MaterialPurchase` agar `Base.metadata` sinkron dengan migrasi (tidak wajib untuk runtime, tapi mencegah drift `alembic --autogenerate`).
*   **Tidak ada perubahan kolom / tipe data.** `manual_hpp_*` tetap `NUMERIC(14,4)`.

## 4. API Contract (FastAPI)
*   **Endpoints (tidak ada breaking change):**
    *   `POST /api/v1/products/{sku}/sizes/{size_id}/stock-from-bahan` — **internal optimization only.**
        *   **Request/Response Body:** Tidak berubah (`AddStockFromBahanRequest` → `ProductSizeDetailOut`).
        *   **Optimasi:**
            1.  Gabungkan `product` + `size` lookup menjadi single JOIN query (atau 1 query `ProductSize` dengan `joinedload(product)` + check `sku` mismatch), hemat 1 round-trip.
            2.  Untuk path `material_purchase_id == None` (FIFO), limit candidates ke `WHERE remaining_length_cm > 0` + gunakan indeks baru; jangan `SELECT *` semua purchases lalu filter Python — push filter ke SQL.
            3.  Untuk `_fifo_deduct_hardware`, ganti `SELECT * WHERE material_id = ? ORDER BY purchased_at` + loop Python yang scan semua purchases menjadi **single `SELECT ... FOR UPDATE` dengan `WHERE remaining_qty > 0 OR remaining_length_cm > 0`** agar tidak load purchases kosong.
            4.  Gabungkan post-commit `_size_detail_out` dari 5 query menjadi **2 query batched**: (a) single `SELECT SUM(change_qty), SUM(CASE WHEN reason='production' ...), SUM(CASE WHEN reason IN ('initial','adjustment') ...)` untuk stok, (b) single batched HPP lookup (reuse `_latest_hpp_map` + `_fabric_items_map` + `_hardware_items_map` yang sudah batched untuk list — tapi untuk single size, tetap 1 query per map, bukan 5 sequential individual). Target: `stock-from-bahan` turun dari ~13 → ~6-7 round-trip.
    *   `PATCH /api/v1/products/{sku}/sizes/{size_id}` — **internal optimization only.**
        *   **Request Body:** `ProductSizeUpdate` (unchanged).
        *   **Response Body:** `ProductSizeOut` (unchanged) — tetap include `current_stock_qty`, `production_stock_qty`, `manual_stock_qty`.
        *   **Optimasi:**
            1.  Gabungkan `_stock_breakdown` + `_current_stock_qty` menjadi satu query: `SELECT SUM(change_qty), SUM(CASE reason='production'), SUM(CASE reason IN ('initial','adjustment')) WHERE product_size_id = ?` — hemat 1 round-trip + 1 seq scan (apalagi setelah ada indeks, scan jadi index-only).
            2.  Gabungkan `product` + `size` lookup seperti di atas.
            3.  Pertimbangkan `db.commit()` + `db.refresh(size)` tanpa re-query stok jika `selling_price`/`manual_hpp_*` yang diubah bukan stok — tapi stok tetap harus di-return, jadi single aggregated query di atas wajib tetap jalan (tidak bisa di-skip).
*   **Validation & Errors:** Tidak berubah (`400` spec_id mismatch, `404` size not found, `409` insufficient fabric).
*   **Alternative considered & rejected:** Mengubah response `stock-from-bahan` untuk **tidak return `ProductSizeDetailOut`** (hanya return `StockLedger` row seperti `POST /stock/adjustments`) akan hemat 5 query post-commit, tapi itu **breaking change** untuk iOS (`TambahStokSheet` mengharapkan `latest_hpp_breakdown` + `current_stock_qty` untuk update UI tanpa re-fetch). Ditolak untuk v3.57; bisa dipertimbangkan sebagai `?return=minimal` optional di iterasi berikutnya jika profiling masih menunjukkan post-commit sebagai bottleneck setelah indeks.

## 5. Frontend Changes (SwiftUI)
*   **Codable Models & APIService:** Tidak ada perubahan. `APIService.addStockFromBahan()` dan `APIService.updateProductSize()` tetap decode `ProductSizeDetailOut` / `ProductSizeOut`.
*   **Views & Controllers:** Tidak ada perubahan wajib. Opsional: tambahkan `os_signpost` / `CFAbsoluteTimeGetCurrent()` logging di `ProdukSizeDetailView` untuk mengukur `TimeInterval` sebelum/sesudah call, agar QA bisa verifikasi p95 <400 ms tanpa perlu backend logs.
*   **Jika ingin maximal gain tanpa backend change:** iOS bisa debounce / optimistic update, tapi bukan scope v3.57.

## 6. Verification & Test Plan
*   **Smoke Test:**
    *   `alembic upgrade head` berhasil di Supabase (atau local Docker Postgres) — `SELECT indexname FROM pg_indexes WHERE tablename IN ('stock_ledger','production_batch_item','material_purchase')` menunjukkan indeks baru.
    *   App compile, `ProdukListView` → `ProdukSizeDetailView` → Tambah Stok 1 pcs → success, tidak crash.
    *   `PATCH /products/{sku}/sizes/{size_id}` dengan `selling_price` baru → 200, stok qty tetap konsisten.
*   **Sanity Test Scenarios (wajib ukur latency):**
    1.  **Baseline measurement (WAJIB sebelum fix):** Jalankan `EXPLAIN (ANALYZE, BUFFERS)` untuk query lambat di Supabase:
        ```sql
        EXPLAIN (ANALYZE, BUFFERS) SELECT COALESCE(SUM(change_qty),0) FROM stock_ledger WHERE product_size_id = '<uuid>';
        EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM material_purchase WHERE material_id = '<uuid>' ORDER BY purchased_at;
        EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM production_batch_item JOIN production_batch ON ... WHERE product_size_id = '<uuid>' AND status='confirmed' ORDER BY confirmed_at DESC;
        ```
        Catat `Execution Time` + `Buffers`. Harus terlihat `Seq Scan` sebelum fix.
    2.  **After index:** Ulangi EXPLAIN — harus jadi `Index Scan` / `Index Only Scan`, `Execution Time` turun >80%.
    3.  **stock-from-bahan E2E (qty=5, single fabric layer, tanpa material_purchase_id):** Dari kain dengan 3 purchases tersisa, FIFO harus deduct benar (remaining_length_cm berkurang total `qty * cut_height_cm`), `MaterialUsageLog` tercatat, `stock_ledger` +1 row `reason='production'`, response `current_stock_qty` naik 5, `production_stock_qty` naik 5, `manual_stock_qty` tetap. Latency p50 <400 ms diukur dari `curl -w "%{time_total}"` atau Cloud Run logs.
    4.  **stock-from-bahan dengan `material_purchase_id` spesifik + insufficient (409):** Pin ke purchase dengan sisa 10 cm, minta qty butuh 20 cm → 409 `Insufficient remaining fabric`, tidak ada ledger row tercipta, latency tetap <400 ms.
    5.  **PATCH selling_price + manual_hpp:** `PATCH {"selling_price": 50000, "manual_hpp_fabric": 1200}` → 200, `selling_price` terupdate, `manual_hpp_total` = 1200 + existing lainnya, `current_stock_qty` tetap sama (tidak terpengaruh patch harga). Latency <300 ms (lebih ringan dari stock-from-bahan).
    6.  **PATCH concurrent (race sanity):** 2 PATCH simultan ke size yang sama (beda harga) → tidak deadlock, final value salah satu (last-write wins, sesuai `pool_size=3` di `scalability-plan.md`), stok tidak korup.
    7.  **Regression — list endpoints tetap cepat:** `GET /products/{sku}/sizes` dan `GET /product-sizes?page=1&limit=50` tetap <500 ms (memakai `_stock_qty_map` batched + indeks baru, tidak regresi).
*   **Load / Soak (opsional, jika ada waktu):**
    *   Seed 10k `stock_ledger` rows (via script) untuk satu size, lalu benchmark `PATCH` sebelum/sesudah indeks — harus tunjukkan constant time setelah indeks (index scan) vs linear sebelum.
    *   `pg_stat_statements` atau Supabase Dashboard → Slow Query Log tidak lagi menampilkan `stock_ledger` SUM di top 5 setelah deploy.
*   **Rollback plan:** Jika indeks menyebabkan write slowdown measurable (>5% insert latency), drop indeks terlemah (`ix_stock_ledger_created_at`) terlebih dahulu — yang kritis hanya `product_size_id` variants.
