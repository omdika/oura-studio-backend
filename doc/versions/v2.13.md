## Task 1 — 5 HPP components at confirm: verified against `app/services/hpp.py` + `production.py`

| Component | Formula in code | Matches check doc? |
|---|---|---|
| `hpp_fabric` | `item.fabric_cost_per_piece` (already a per-piece rate, set from `cutting_layout_item.cost_per_piece` at batch creation) | **Not literally** — see flag below |
| `hpp_labor` | `pattern_spec.est_labor_minutes × settings["labor_rate_per_minute"]` | ✅ |
| `hpp_overhead` | `settings["default_overhead_per_unit"]` | ✅ |
| `hpp_pooled_material` | `SUM(settings WHERE key LIKE 'pooled_material_rate:%')` | ✅ functionally (generalizes the literal `thread + packaging` sum to any number of pooled-rate settings, same result today since those are the only two keys used) |
| `hpp_hardware` | previously `SUM(component.qty_per_unit × material.current_avg_cost)` over **all** `PatternComponent` rows for the spec, no material-type filter | ❌ **was missing the filter — fixed** |

### Flag: `hpp_fabric = cost_per_piece × qty_actual` (as written in the check doc) is wrong for this codebase

`cutting_layout_item.cost_per_piece` is computed in `allocate_cost_per_piece()`
(`app/services/cutting_optimizer.py:291`) as `(fabric_cost_share) / qty_suggested` — it is
**already a per-piece rate**, not a batch total. Every other place `hpp_total` (and by extension
`hpp_fabric`) is used treats it as a **per-unit** cost: `stock_ledger.unit_hpp_snapshot`,
`compute_margin_pct(selling_price, hpp_total)` (against a per-unit `selling_price`), Price
Advisor, sales order `line_profit`. Multiplying by `qty_actual` a second time at confirm would
silently turn every one of those into a batch-total-vs-per-unit-price mismatch — margins, stock
valuation, and RINCIAN HPP itself (which the whole feature this doc is about is titled around
showing a **per-piece** "~kain Rp.../pcs" hint) would all be wrong for any `qty_actual != 1`.
Verified via isolated test (below): current code (no re-multiplication) is correct. Not changed.

### Fix applied: `hpp_hardware` now filters by material type

`_hardware_cost_per_unit()` in `app/routers/production.py` now joins to `Material` and filters
`category = 'hardware' AND cost_class = 'direct_precise'`, matching the check doc's formula.
Previously it summed **every** `PatternComponent` row regardless of the referenced material's
category — `POST /pattern-specs` only validates that a component material has a purchase on
record, not that it's actually a hardware material (the iOS picker UI restricts this, but nothing
enforced it server-side). Verified with a deliberately-wrong "decoy" thread-category component
attached to a test spec: before the fix its cost would have leaked into `hpp_hardware`; after,
it's correctly excluded.

## Task 2 — `GET /products/{sku}/sizes` `latest_hpp_breakdown`: verified + one fix

- Confirmed-only filter (`production_batch.status = 'confirmed'`): already correct, unchanged
  (this was the v2.8 stale-draft fix).
- Response key names (`fabric`, `pooled_material`, `hardware`, `labor`, `overhead`, `total`):
  already correct (v2.10 rename), re-verified — no typos/mixed case.
- **Ordering fix:** `_latest_production_item` / `_latest_hpp_map` (products.py) and
  `_avg_margin_pct` (reports.py) previously ordered candidates by `ProductionBatch.produced_at
  DESC`. Since `production_batch.confirmed_at` now exists (added this session, see v2.12), these
  now order by `confirmed_at DESC NULLS LAST, produced_at DESC` instead — matching the check
  doc's `ORDER BY batch.confirmed_at DESC`, with a `produced_at` fallback for ties and for batches
  confirmed before this column existed (they have `confirmed_at = NULL`; Postgres' default `DESC`
  ordering is `NULLS FIRST`, which without the explicit `nullslast()` would wrongly rank an old
  unmigrated batch ahead of a genuinely more recent confirm).

This was **not** a theoretical fix — testing against the live DB during this verification showed
real confirmed batches created via the currently-deployed (pre-`confirmed_at`) API all have
`confirmed_at = NULL` right now, so a plain `confirmed_at DESC` (no `nullslast`, no fallback)
would have made "latest confirmed item" selection non-deterministic for any product_size with 2+
confirmed batches until every existing batch ages out. Confirmed the fallback resolves this: for
a real product_size with 2 confirmed items (both `confirmed_at = NULL`), the endpoint correctly
picks the one with the later `produced_at` — same item it would have picked before this change.

## Task 3 — End-to-end verification (isolated test data, not real business data)

Built a fully isolated product/material/spec/batch (SKU `HPPTEST-SKU3`, deleted after the test —
see cleanup note) to confirm a real batch through the actual endpoint without touching real
inventory or locking real HPP data. Inputs: `fabric_cost_per_piece=3400.0` (set directly, standing
in for a cutting-layout-derived value), `est_labor_minutes=10`, hardware component
`qty_per_unit=2` on a material with `current_avg_cost=500.0` (from a real purchase), plus a
deliberately-wrong "decoy" `thread`-category component (`qty_per_unit=1`,
`current_avg_cost=999999.0`) to prove the hardware-filter fix works. Settings used:
`labor_rate_per_minute=250.0`, `default_overhead_per_unit=200.0` (both real, already configured),
plus temporary `pooled_material_rate:thread=100.0` / `pooled_material_rate:packaging=50.0`
(removed after the test — see gap below, these are **not** configured in production).

`POST /production-batches/{id}/confirm` response:

```json
{
  "hpp_fabric": 3400.0,
  "hpp_pooled_material": 150.0,
  "hpp_hardware": 1000.0,
  "hpp_labor": 2500.0,
  "hpp_overhead": 200.0,
  "hpp_total": 7250.0
}
```

`GET /products/{sku}/sizes` immediately after, for the confirmed size:

```json
{
  "current_stock_qty": 5,
  "production_stock_qty": 5,
  "manual_stock_qty": 0,
  "latest_hpp_breakdown": {
    "fabric": 3400.0,
    "pooled_material": 150.0,
    "hardware": 1000.0,
    "labor": 2500.0,
    "overhead": 200.0,
    "total": 7250.0
  },
  "margin_pct": null

```

All 6 keys present, non-zero (except `margin_pct`, correctly null — no `selling_price` set on
the test size), decoy component correctly excluded from `hpp_hardware` (1000.0 = 2 × 500.0, not
2000999.0). Test data (product, sizes, materials, purchases, pattern spec, batch/item, stock
ledger rows, temp settings) fully deleted afterward — confirmed via `GET
/products/HPPTEST-SKU3/sizes` → 404, and `month_batches_confirmed` back to its pre-test count.

## Operational gap flagged, not fixed (not a code issue)

`pooled_material_rate:thread` and `pooled_material_rate:packaging` are **not currently set** in
the live `settings` table (only `labor_rate_per_minute` and `default_overhead_per_unit` exist).
`_pooled_material_rate_sum()` sums over whatever `pooled_material_rate:%` keys exist, so this
isn't a code bug — but it means **every real batch confirmed right now gets `hpp_pooled_material
= 0`**. Needs the business owner to set real values via whatever Settings entry point the app
exposes for these two keys before RINCIAN HPP's "Bahan Pooled" line will be meaningful for new
confirms. Historical confirmed batches with a non-zero `hpp_pooled_material` reflect settings that
were configured at their own confirm time (HPP is snapshotted, not recomputed) — not evidence
these settings are configured now.
