# v2.4 — Live Backend Integration: API Contract Clarifications
**Date:** 2026-08-07  
**Changed by:** Frontend (discovered during live integration testing)

---

## Summary

First live connection of the iOS app to the FastAPI backend deployed on Google Cloud Run. Every major screen had decode failures because the actual backend JSON format differed from the frontend's Swift model structs. This document records all behavioral discoveries and contract clarifications found during integration — they represent gaps in the Section 4 API contract that the backend should treat as binding additions.

**Backend URL tested:** `https://oura-backend-jkt-763614853578.asia-southeast2.run.app/api/v1`

## 1. Response Format Clarifications

### 1.1 GET /pattern-specs — Flat format, not nested

The frontend originally assumed the response would include `product_name`, `size_label`, and a `fabrics[]` array. The actual backend format is flat:

```json
{
  "id": "...",
  "product_size_id": "...",
  "fabric_material_id": "...",
  "cut_width_cm": 21.0,
  "cut_height_cm": 90.0,
  "rotation_allowed": true,
  "est_labor_minutes": 12.0,
  "is_active": true,
  "effective_from": "...",
  "effective_to": null,
  "components": [{ "id": "...", "material_id": "...", "qty_per_unit": 1.0 }]
}
```

**This format is correct.** The frontend was updated to decode as `BackendPatternSpec` and enrich client-side. No backend change needed.

### 1.2 GET /products/{sku}/sizes — Flat format, no stock breakdown

The frontend assumed the sizes list would include `product_sku`, `product_name`, `production_stock_qty`, `manual_stock_qty`. Actual format:

```json
  "product_id": "...",

  "reorder_min_qty": null,
  "selling_price": null,
  "is_archived": false,
  "current_stock_qty": 3
}
```

**This format is correct.** Frontend adapted. No backend change needed.

### 1.3 POST /cutting-optimizer/suggest — Response has no IDs, no product names


**This format is correct.** Frontend generates UUIDs client-side and enriches names. No backend change needed.

Frontend assumed the response was a full `CuttingLayout` object. Actual response:


### 1.5 GET /production-batches — Items missing `production_batch_id`, `product_name`, `size_label`

Frontend assumed batch items included their parent batch ID and human-readable product/size names. Actual batch item format:

```json
{
  "id": "...",
  "product_size_id": "...",
  "pattern_spec_id": "...",
  "qty_actual": 9,
  "cutting_layout_item_id": "...",
  "material_purchase_id": "...",
  "fabric_cost_per_piece": 5000.0,
  "fabric_length_per_unit_cm": 11.1,
  "hpp_fabric": 0.0,
  "hpp_pooled_material": 0.0,
  "hpp_hardware": 0.0,
  "hpp_labor": 0.0,
  "hpp_overhead": 0.0,
  "hpp_total": 0.0
}
```

**Important discovery:** All `hpp_*` fields are `0.0` for batches in draft status. HPP is only computed when the batch is confirmed. **However, `fabric_cost_per_piece` is populated even in draft.** The frontend uses this as a partial HPP estimate while the batch is pending — showing it as `~kain Rp.../pcs` instead of `HPP Rp0/pcs`.

**This format is correct.** Frontend adapted. No backend change needed.

## 2. POST /pattern-specs — Critical Contract Corrections

These are **actual contract bugs** — the frontend was wrong and the backend was right, but the Section 4 contract was ambiguous enough to have caused the frontend to use the wrong format.

### 2.1 Request body must be flat (not a `fabrics[]` array)

**Frontend was sending:**
```json
{
  "product_size_id": "...",
  "fabrics": [{ "material_id": "...", "cut_length_cm": 90, "cut_width_cm": 21, "rotation_allowed": true }],
  "est_labor_minutes": 22,
  "components": [...]
}
```

**Backend actually expects:**
```json
{
  "product_size_id": "...",
  "fabric_material_id": "...",
  "cut_width_cm": 20,
  "cut_height_cm": 100,
  "rotation_allowed": true,
  "est_labor_minutes": 22,
  "components": [{ "material_id": "...", "qty_per_unit": 1.0 }]
}
```

**Update Section 4** — `POST /pattern-specs` request body: flat structure (not nested under `fabrics`), field is `fabric_material_id` (not `material_id`), long dimension is `cut_height_cm` (not `cut_length_cm`).

### 2.2 `est_labor_minutes` must be > 0

Backend returns 422 if `est_labor_minutes` is 0 or missing. The frontend now enforces this client-side (`canSave` blocks if labor is 0). **Update Section 4** — document this validation constraint explicitly: `est_labor_minutes` is required and must be greater than 0.

### 2.3 One fabric per spec (backend's assumption is already correct)

The frontend spec originally described multi-fabric specs as a future possibility. The backend has always been one-fabric-per-spec (flat `fabric_material_id`). **This is the confirmed permanent design.** Section 4 should reflect this explicitly: each `PatternSpec` maps to exactly one `(product_size, fabric_material)` pair.

## 3. PATCH /products/{sku} — Soft Archive Discovery

**Discovery:** `DELETE /products/{sku}` performs a hard delete with cascade to `product_sizes` and their `pattern_specs`. This destroyed resep history when a product was archived — an unacceptable data loss.

**Correct behavior (confirmed via PATCH):**
- `PATCH /products/{sku}` with `{ "name": "...", "is_archived": true }` performs soft archive ✅
- Requires `name` in the body even when only changing `is_archived`
- Setting `is_archived: false` via PATCH is silently ignored — archive is one-way
- `POST /products/{sku}/archive` returns 404 (route does not exist)

**PATCH /products/{sku}/sizes/{sizeId}:**
- Accepts `{ "is_archived": true }` without requiring other fields
- Same one-way soft archive behavior

**Update Section 4** — document that client-side archiving of products and sizes should use PATCH with `is_archived: true`, NOT DELETE. Add warning note that DELETE is a hard cascade delete and is destructive.

## 5. Section 4 Updates Required

The following additions should be made to Section 4 of `doc/handoff.md`:

| Endpoint | Update |
|---|---|
| `POST /pattern-specs` | Request body is flat (not `fabrics[]`), fields are `fabric_material_id`, `cut_width_cm`, `cut_height_cm`; `est_labor_minutes > 0` required |
| `GET /production-batches` | `hpp_*` fields are 0.0 in draft; `fabric_cost_per_piece` is populated in draft as partial estimate |
| `PATCH /products/{sku}` | Soft archive — requires `name` alongside `is_archived: true`; is_archived is one-way (can't unarchive via PATCH) |
| `DELETE /products/{sku}` | Add warning: hard delete with cascade — destroys sizes and pattern specs |
| `POST /cutting-optimizer/layouts` | Response is `{ cutting_layout_id }` only, not a full layout object |
